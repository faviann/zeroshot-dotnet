# Broodling's reusable Zeroshot consumer boundary

Research for [Identify the reusable boundary in Broodling's DirectTarget client](https://github.com/faviann/zeroshot-dotnet-sdk/issues/3), inspected 26 September 2026. This is decision input for the SDK, minimal .NET CLI and Broodling adoption plan. API shape, SDK transport implementation, distribution and additional capabilities remain decisions.

## Evidence and finding

The selected HTTP/OECP integration already exists in Broodling. [Replace DirectTarget's client bridge with HTTP/OECP integration][implementation] merged on 25 September at `70cda96554524fbf4c7bb9daa20df18dbc470a0b`. This audit uses the later Broodling commit `fdd0013ea7555c9ee634f6d94268856365235d81`, including subsequent TLS, reference-access and service changes. Broodling's declared profile is .NET 10 / Linux x86-64 with native Zeroshot 10.3.0, source `054ad3fd6c763b98d12f5b2e90830b97116561ad`, executable SHA-256 `afeb4372eaa63c3d88b308bd32afa5b888297fc0a82aa879542daf1437a6ee06`. HTTP DirectTarget operation requires no Python client. Python SDK 10.3.0.post1 still serves the separate LocalTarget bridge and supplied the native executable used to generate the approved execution asset. These are consumer constraints, not a settled SDK-wide support policy. [Current architecture][authority], [native pins][pins], [asset decision][asset-decision].

**Finding:** the reusable candidate is target discovery, one-shot submission, reconnection to an identified run, bounded status, terminal waiting and explicit force. Broodling already separates those operations from SQLite authority and Git custody. Its application must continue to decide when a send is authorized, what constitutes retained correlation, and whether an observed result can complete an Attempt. This boundary is an inference from the [submission adapter][submission], [session reader][session], [run operations][run] and [application dispatch][dispatch]; it does not select a public SDK API.

The governing decisions were read in full: [Choose the approved DirectTarget submission mechanism][asset-decision], [Define the resources owned by an HTTP DirectTarget Attempt][resource-decision], [Define Broodling's accepted HTTP/OECP contract][protocol-decision], [Define durable HTTP dispatch identity and recovery][recovery-decision], and [Define legacy bridge compatibility during the HTTP transition][fresh-state]. Their old bridge migration passages were superseded by the last decision. Current source and tests establish implementation at the recorded revision.

## Actual consumer operations

Here, reconnecting to an exact run means creating an OECP session and naming that run in each request. It does not mean using the execution-level `run/attach` operation. Broodling's reader calls only `initialize`, `run/status` and `run/force`. [Session implementation][session].

| Operation | Inputs, behavior and outputs today |
| --- | --- |
| Offline preparation | `PrepareHttpSubmission` starts from admitted Attempt authority, exact B1, approved graph/runtime and canonical target origin. It pins B1, freezes a secret-free request plus caller-allocated UUIDv7, submission key, asset bytes and local binding in SQLite. It makes no target call and requires no dispatch credentials. [Preparation][prepare]. |
| Discovery | Each public network operation reads `/.well-known/zeroshot-native-v2`; a healthy wait reuses its connection. Broodling requires its stock dialect, controller audience, no authentication and exact run/session/OECP routes. Discovery alone does not verify the deployed executable or native state identity. [Discovery][discovery], [protocol decision][protocol-decision]. |
| Submission | The application commits dispatch intent before adapter discovery and releases its SQLite writer. The adapter sends the retained `runId` and `submission` containing title, graph, runtime, task, repository, target branch, exact revision and key; it adds current connection values and `githubToken` in memory. It returns successfully only for HTTP 200 containing exactly the expected run ID. HTTP 409 `request.conflict` becomes a conflict without an adoptable diagnostic ID. [Dispatch][dispatch], [wire submission][submission]. |
| Session setup | Supply retained origin, run ID, title, size and source repository/branch/revision. Discovery precedes `{runId}` posted to `/native-v2/oecp-session`; its WebSocket endpoint must match the origin's paired `ws`/`wss` authority and route, with no bearer token. Broodling validates the pinned initialization response. Neither session creation nor initialization confirms that the run exists or that this complete submission was accepted. Every status/force still names the run explicitly. [Session setup][session], [accepted contract][protocol-decision]. |
| Bounded observation | `ObserveAsync` uses the confirmed ID, or the intended ID after dispatch intent. A merely prepared record makes no contact. It validates the returned binding and exposes phase/active node names in timestamped `Available` or `Unavailable` output, annotated intended/confirmed. It stores no result or correlation. Cancellation propagates. [Observation][observe], [projection validation][projection]. |
| Wait / reconnect | Application `WaitAsync` requires correlation before contact, or returns an already-retained completion offline. The persistence-free wait opens a fresh session, reads immediately, then polls every two seconds following a nonterminal reply. One healthy wait has no overall job deadline. Network failure/cancellation detaches it; a later wait reopens the same retained run without submission, dispatch credentials or execution checkout. Its result is run ID, success/failure and opaque success JSON. [Run wait][run], [completion][completion]. |
| Explicit stop | Broodling commits abandonment first. A confirmed ID can be forced directly; an intended ID requires a matching status precheck. The same session/budget covers setup, precheck, a single force and any terminal polling. Transport outcome is `NotSent`, `Uncertain` or `Terminal`; cancellation propagates even after force may have been sent. Public Broodling stop preserves quarantine: terminal observation becomes `CessationUnconfirmed(true)`, no force becomes `CessationUnconfirmed(false)`, uncertain force becomes `NativeTransportError`. [Run stop][run], [application stop][stop]. |
| Completion | Success JSON reaches Broodling's exact authorized PR-receipt validator. It fetches/pins the accepted revision before the final authority recheck and atomic receipt/disposition write. Native failure abandons through the application; uncorrelated progress/stop cannot complete it. [Completion][completion]. |

The approved graph/runtime asset is 77,069 bytes, identified by SHA-256 `10f410b4a3ba06f69ead07b5d281d289fd6e378854bcb0600b1d963bdfce55d8`. That byte identity and the approved Codex/gateway/model policy belong to Broodling. Native tooling generated the asset; C# passes its values through without template expansion. [Asset loader][asset], [asset decision][asset-decision].

## Protocol facts, reusable behavior and application policy

| Concern | Native or protocol fact | Reusable capability to consider | Broodling choice that must stay distinguishable |
| --- | --- | --- | --- |
| Submission identity | Native serializes `RunSubmission` for its digest. Its ledger resolves the same key/digest to an existing run; a changed digest conflicts. The outer proposed run ID and credentials are outside that digest, so an exact replay can return the earlier ID. [Native digest][native-digest], [native resolution][native-resolve], [production submission][native-submit]. | Submit a caller-supplied identity/payload once and expose the acknowledgement or classified failure accurately. | Broodling reserves one UUIDv7 per Attempt, rejects an acknowledgement for any other ID, and owns replay authorization and correlation. [Dispatch][dispatch]. |
| Credentials | Explicit connection values and source token are outside submission identity. Native deduplication precedes reconstruction of the replacement secret environment; rotating replay credentials does not refresh an accepted run's credentials. [Native request][native-request], [production submission][native-submit]. | Supply current credentials separately from externally retained immutable material; avoid secret-bearing diagnostics. | Fixed `gateway`/`github` names, allowed environment fields and exact gateway URL are its profile policy. Credential providers and rotation timing remain caller concerns. [Pins and credentials][pins], [wire submission][submission]. |
| Run state and output | Native status contains identity/source/size/cursor and a closed admitted/running/stopping/finished union. Success output is graph-owned JSON; force returns a status projection and repeated force is ledger-idempotent. [Native status/force types][native-observation]. | Decode coherent projections and expose terminal output without inferring application success. | Broodling requires exact run/title/source/size, drops validated token metadata, uses cursors only as strings, normalizes failure labels, and validates the specific seven-field PR receipt. [Projection][projection], [receipt policy][receipt]. |
| Durability | The observer can expose an in-memory `finished/failed/runtime_failed` fallback without a new durable terminal event; later durable terminal data takes precedence. A generic finished projection is therefore insufficient proof that all terminal evidence is durable. [Native runtime fallback][native-fallback], [fallback tests][native-fallback-tests]. | Preserve the difference between observation, transport acknowledgement and application retention. | Broodling's retained completion and Git custody are its own durable facts. [Completion][completion]. |
| Schema and identity checks | Pinned native request and observation types reject unknown fields; discovery identifies a protocol shape, not executable/image attestation. [Native request][native-request], [native status][native-observation], [accepted contract][protocol-decision]. | Validated framing, bounded decoding, endpoint checks, and enough returned identity to validate retained expectations. | Exact stock discovery/initialization equality, supported native/image pins and asset approval are its reviewed compatibility policy. A more permissive SDK default must not silently relax it. [Discovery][discovery], [session][session], [target readiness][readiness]. |
| Limits and waiting | The wire permits status and force; client budgets do not constrain job duration or prove remote cessation. [Native status/force][native-observation]. | Cancellable operations with enclosing deadlines, bounded payloads and truthful detachment/uncertainty. | Current constants: progress 10s; submit 60s; stop 30s; wait setup/first read 30s, later reads 10s; polling 2s; HTTP/incoming WebSocket JSON 4 MiB; outgoing WebSocket 1 MiB; response headers 32 KiB; depth 64. These values and polling over watch were explicit consumer decisions. [Limits][limits], [protocol decision][protocol-decision]. |
| TLS and connection behavior | The chosen target is reached by its retained origin; transport must not substitute a foreign endpoint. [Session validation][projection]. | Verified HTTPS/WSS, caller-supplied trust and cancellation/lifetime control. | Broodling disables redirects, proxies, cookies and ambient credentials. It uses system trust or exactly one configured PEM root, reloaded per new TLS connection, with hostname checks; root location is external operator configuration. Any adopted implementation must preserve that deployment path. [TLS handler][tls], [trust witnesses][trust-tests]. |
| Retries and recovery | Native idempotency supports equivalent replays; it cannot decide whether Broodling still authorizes another send. [Native resolution][native-resolve]. | Allow the caller to decide whether/when another operation starts; expose sufficient failure information. | The transport retries nothing. Current application services separately retry eligible dispatch/wait operations, using durable authority and fixed classifications. An SDK retry loop could bypass those gates or nest delays. [Run operations][run], [submission progression][progression], [completion observer][observer]. |

Broodling's seven-string receipt requires `version=v1`, `mode=pr`, `outcome=opened`, the expected repository and PR target, a non-B1 lowercase 40-hex `headRevision`, and a nonempty decimal `pullRequestId`. That is a workflow-specific consumer acceptance contract; generic native success output can be null or another JSON shape. [Receipt validation][receipt], [terminal decoding][projection].

## Facts the application must retain and decisions it must keep

Broodling's `http.v1` row holds the complete secret-free request, immutable key, intended ID, asset reference and target/native/local-Git binding. Its separate phase, confirmed ID and monotonic replay-conflict fact have SQL guards. Asset bytes live in immutable content-addressed rows. These facts exist before the SDK can send anything. [Persisted model][submission-model], [SQL guards][schema], [preparation][prepare].

Adoption needs a way to preserve externally owned facts, whether the SDK accepts a retained envelope, exposes a lossless typed representation, or uses another design. **A caller-supplied immutable submission and independently reopenable run binding are design options, pending the API decision.** The existing code establishes these required outcomes:

1. Preparation works offline; replay preserves the intended ID, key, task, source and approved runtime. Installed asset changes or loss cannot regenerate an existing submission. Current credential values remain separate. [Preparation and replay validation][prepare], [retained asset tests][retained-tests].
2. Every send/replay passes current authority, pause, conflict, credential and B1-custody checks. Intent commits before discovery; no SQLite writer spans network I/O. An SDK operation must not perform hidden submission during preparation or reconnection. [Dispatch ordering][dispatch], [ordering test][dispatch-tests].
3. Lost acknowledgement remains unresolved. Matching status, including finished status, cannot establish full-submission correlation because status lacks the key and graph/runtime digest. Conflict blocks future sends but cannot erase an exact acknowledgement already in flight. Both acknowledgement/conflict orderings converge in the application. [Recovery decision][recovery-decision], [concurrency tests][concurrency-tests].
4. A late exact acknowledgement can be retained after abandonment, pause or local custody loss. Broodling then attempts stop without restoring authority. Unknown-run stop, caller death and local initiation drainage cannot fence a request already buffered remotely. [Dispatch][dispatch], [late acknowledgement tests][late-tests], [buffered request witness][buffered-test].
5. Observation/control require the retained target/run/source expectations, current TLS trust and cancellation, rather than dispatch credentials or an old checkout. Successful result acceptance additionally requires Broodling's authority and Git custody. Already-retained completion remains available offline. [Observation][observe], [completion][completion], [stop][stop].

## Adoption and persistence constraints

**Preserve the existing stored request text.** `RequireRetainedHttpSubmission` compares `request_json` as a string against its supported reconstructions; the SQL trigger forbids rewriting it. It accepts both the current task projection and the projection from before on-demand reference access. `binding_json` is checked structurally, while exact asset bytes have their own hash. The sending adapter reparses the stored request and serializes an augmented credential-bearing body, so its network bytes need not equal the stored text. Preserving that local string contract and native submission identity are separate obligations. A new serializer that normalizes saved text or injects defaults could violate one of them. [Replay validation][replay-validation], [immutable storage][schema], [wire construction][submission].

The existing compatibility witness has a precise scope: `BundleBoundRequestFrozenBeforeReferenceAccessReplaysWithItsExactBytes` uses `BundleHttpFixture.PrepareAsEarlierRelease` to synthesize the older task projection from current admitted facts, insert it into a freshly initialized **current-schema** store, mark it dispatched, reopen, and replay through a controlled target. It proves preservation of that supported request projection and submitted values. It does **not** open an archived release database, execute the older binary, prove arbitrary schema/native compatibility, or exercise real-native cross-release replay. [Compatibility test][projection-test], [fixture construction][projection-fixture].

The earlier fresh-state scope excluded pre-transition bridge stores; it also explicitly retained restart/reopen/replay obligations for newly created HTTP state. It authorizes no further reset for SDK adoption. At this audit revision, stores identify both schema version and definition hash; `upgrade-store` implements no earlier-identity upgrade. Unfrozen schema-1 candidate builds may already refuse each other's stores. An adoption plan must state its supported starting application/native identities and preserve compatible state, or obtain a separate explicit disposition for an actual incompatible change. [Fresh-state decision][fresh-state], [store lifecycle][store], [release/schema policy][release-schema].

The direct client is wired through internal static calls. `INativeReader`, `INativeStopper`, `INativeTransport` and `ZeroshotTransport` belong to the bridge path; supplying those to HTTP wait/observe/stop does not replace the direct implementation. Adoption has call sites in preparation/dispatch, observation, wait, stop, origin validation and target-readiness discovery. Broodling's public `NativeSubmission`, `NativeResult`, `NativeObservation`, `InvocationTarget.Direct`, callable methods and safe exception classifications are existing contracts. Mapping an SDK underneath those contracts is an option that avoids making SDK types part of their persisted or public representation. [Bridge interfaces][bridge], [invocation routing][invocation], [observation][observe], [completion][completion], [stop][stop], [readiness][readiness], [public errors][errors].

## Effect of the latest-native preference

The user prefers the latest native release unless it substantially changes the design, with 10.3.0 as the fallback. The live release API reports **10.9.0**, published 26 September 2026 at `75ae54b6693b6ae4cedeedd37a79ce3919d9a8fa`. This bounded follow-up inspects the consumer's upgrade coupling; the separate native research owns the full version comparison. [Latest native release][latest-release].

Supporting both native versions in the SDK and upgrading Broodling's target are separate work. Broodling's retained `binding_json` embeds version, source commit and executable SHA, and replay/completion validation compares it with bindings generated from the current compiled pins. Changing those constants alone makes existing rows fail this check. Similarly, `ExecutionAsset.FromRetained` accepts only the one compiled approved asset SHA. An SDK package reference cannot resolve those application compatibility decisions. [Retained-binding validation][replay-validation], [pins][pins], [asset validation][asset].

One concrete semantic change is already established: 10.9.0's default PR template selects `PullRequestV2`, whose receipt is `v2`/`ready`; Broodling accepts only `v1`/`opened`. Native 10.9.0 still recognizes the original PR worker and has tests for its v1 receipt, so adopting the new default template and upgrading the native executable need not be the same decision. Whether the complete existing approved asset is admissible and equivalent under 10.9.0 remains unproven here. [Latest template][latest-template], [delivery modes][latest-delivery], [receipt tests][latest-delivery-tests], [Broodling receipt validator][receipt].

**Assessment:** the evidence does not establish a need to redesign the SDK boundary, but a consumer native upgrade requires explicit pin/asset approval, retained-state handling, and a receipt decision if it adopts the new template. Keeping Broodling on 10.3.0 while a compatible SDK also supports latest could avoid that consumer upgrade during adoption. These are options for the native-release decision. No native-state transition, latest-native witness or broad backward compatibility was validated in this research.

## Candidate extraction boundaries

These are recommendations for the later design decision, not selected implementation work.

| Candidate | Treatment to consider |
| --- | --- |
| HTTP/WebSocket exchange, JSON/RPC framing, discovery/session validation | Reuse the tested behavior from `DirectTargetExchange` and `DirectTargetSession`; adapt Broodling exception names and retained-binding inputs. Decide where strict release support, TLS construction and limits are configured without broadening the supported consumer behavior. [Exchange][limits], [session][session]. |
| Submission acknowledgement and explicit run operations | Reuse one-shot submit, validated status, cancellable terminal wait and force outcome distinctions. Keep command sequencing observable enough for Broodling's authority gates. Whether polling/precheck lives in SDK convenience methods or its adapter remains an API/lifecycle decision. [Submission][submission], [run operations][run]. |
| Asset approval, request/task assembly, persistence, replay authority, service retry, receipt disposition, custody and maintenance | Keep private to Broodling. Its native-generated asset can be passed through the SDK; its SHA, model/gateway policy, Attempt key prefix, RequestBundle prose, SQLite state and cleanup decisions have no evidence of being general SDK rules. [Asset][asset], [request construction][replay-validation], [schema][schema], [completion][completion], [stop][stop]. |

The consumer gives no demand for logs, execution attach, watch/history, arbitrary profile management, native lifecycle management or a particular new CLI command grammar. Its narrow usage cannot by itself choose those SDK/CLI capabilities. The separate LocalTarget bridge is existing behavior whose replacement, if desired, needs its own explicit scope. [Selected protocol decision][protocol-decision], [target routing][invocation], [SDK scaffold][sdk-readme].

## Validation assets and evidence limits

No builds, test suites, provider tasks or operational changes were run for this research. The following inspected witnesses can support a later implementation gate:

| Witness family | Distinct boundary to preserve |
| --- | --- |
| `DirectTargetExchangeTests`, `DirectTargetSessionTests`, `DirectTargetRunTests` | Actual bounded/chunked/fragmented transport, malformed JSON/RPC/bindings, setup cancellation, no later exchange after timeout, immediate/two-second polling, and one bounded force operation. [Exchange tests][exchange-tests], [session tests][session-tests], [run tests][run-tests]. |
| `DirectTargetTrustTests` | Real loopback HTTPS/WSS with the configured root, wrong root/hostname refusal, root reload between connections and missing-root pre-intent refusal. [Trust tests][trust-tests]. |
| `HttpSubmissionTests`, `HttpDispatchTests`, `DispatchProcessTests` | Real SQLite/Git preparation and replay, unchanged retained content, rotated ephemeral credentials, concurrent conflict/acknowledgement, late acknowledgement, caller death and delayed acceptance after local drainage. [Preparation tests][retained-tests], [dispatch tests][dispatch-tests], [process witness][buffered-test]. |
| `NativeObservationTests`, `AttemptCompletionTests`, `RetirementTests`, service tests | Intended versus confirmed observations, uncorrelated wait refusal, authority-preserving detach, receipt/pin-before-disposition, offline completion, stop/quarantine and service-owned retry. Preserve these at Broodling's public seam when swapping its transport. [Observation tests][observation-tests], [completion tests][completion-tests], [retirement tests][retirement-tests], [progression tests][progression-tests], [observer tests][observer-tests]. |
| `StockDirectTargetTests` | Unmodified pinned native with the approved asset: exact B1 after branch movement, no client checkout, terminal result after target restart, retained offline completion, and missing B1 producing unresolved dispatch followed by exact replay to one failed run. Another case exercises Broodling's reference helper. Provider, forge and receipts are controlled; these are neither live GitHub delivery nor semantic-quality evidence. [Stock-native tests][stock-tests], [witness scope][witness-doc]. |

SDK tests can own protocol/lifecycle behavior. Broodling adoption tests must continue to own persistence and authority. A reference-helper end-to-end case protects the existing consumer but does not turn reference capture/access into SDK responsibility. The existing earlier-projection fixture should be retained; any claim about a released-state adoption path needs an additional fixture for that specifically selected schema/native baseline. These are validation recommendations derived from the witnesses above.

## Questions now precise enough for decisions

1. Under the latest-native preference, does adoption keep Broodling's 10.3.0 target through SDK compatibility, or explicitly upgrade its native/asset binding, and what supported dialects and receipt behavior follow?
2. How will the SDK accept externally retained identity and request material, return acknowledgement separately from status, and reconnect without requiring SDK-owned storage or regenerating a submission?
3. Which layer owns polling, per-operation deadlines, the intended-ID stop precheck, TLS root reload and retry prohibition, so Broodling keeps its established behavior while the SDK remains useful to other callers?
4. Which application/native starting identities and persisted `http.v1` projections will the Broodling adoption gate cover, and can public contracts and current schema remain stable through an internal adapter?
5. Which minimal CLI operations belong to the first release beyond this consumer evidence? Broodling's integration supplies no answer about packaging or broader command breadth.

These questions do not reopen the selected DirectTarget architecture and do not authorize state migration, reset or an operational cutover.
